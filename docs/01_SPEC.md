**Методология:** Spec-Driven Development (SDD)
**Шаг:** 1 — Specify
**Статус:** Draft

---

## 1. Цель проекта

AlbumCatalog — веб-приложение для каталогизации музыкальных альбомов, исполнителей и песен.
Приложение позволяет пользователю вести справочник исполнителей, создавать альбомы, привязывать
к альбомам песни с указанием их порядкового номера в треклисте, и просматривать сквозной каталог
всех песен с информацией о том, в какие альбомы (и под каким номером) каждая песня входит.

**Ключевая особенность предметной области:** песня (`Song`) — самостоятельная сущность, не
привязанная жёстко к одному альбому. Одна и та же песня может присутствовать в нескольких
альбомах (оригинал, сборник, переиздание, live-версия и т.д.), и в каждом альбоме у неё может
быть свой порядковый номер трека.

### Технологический стек

| Слой | Технология |
|---|---|
| Backend | Django 5 (Python) |
| API | Django REST Framework (DRF) |
| Frontend | Vue 3 (Composition API) |
| State management | Pinia |
| Сборка frontend | Vite |

На данном шаге (Specify) код не пишется — документ фиксирует требования и контракты, на основе
которых на следующих шагах (Plan / Tasks / Implement) будет проектироваться архитектура и писаться код.

## 2. Модели данных

### 2.1 Artist (Исполнитель)

| Поле | Тип | Ограничения |
|---|---|---|
| `id` | AutoField (PK) | — |
| `name` | CharField | обязательное, `max_length=255` |

Связи: один исполнитель имеет много альбомов (`Artist 1 — N Album`).

### 2.2 Album (Альбом)

| Поле | Тип | Ограничения |
|---|---|---|
| `id` | AutoField (PK) | — |
| `title` | CharField | обязательное, `max_length=255` |
| `artist` | ForeignKey → Artist | обязательное, `on_delete=CASCADE`, `related_name="albums"` |
| `release_year` | PositiveIntegerField | обязательное; разумные границы (например, 1860–текущий год + 1) |

Связи: альбом принадлежит одному исполнителю; альбом содержит много песен через `AlbumSong`
(many-to-many с дополнительным атрибутом `track_number`).

### 2.3 Song (Песня)

| Поле | Тип | Ограничения |
|---|---|---|
| `id` | AutoField (PK) | — |
| `title` | CharField | обязательное, `max_length=255` |

Песня не имеет прямой ссылки на альбом — связь только через промежуточную таблицу `AlbumSong`.
Это позволяет одной песне входить в несколько альбомов.

### 2.4 AlbumSong (связь Album ↔ Song, "трек в альбоме")

Промежуточная модель many-to-many между `Album` и `Song`, явно объявленная (`through`),
поскольку несёт дополнительный атрибут — номер трека.

| Поле | Тип | Ограничения |
|---|---|---|
| `id` | AutoField (PK) | — |
| `album` | ForeignKey → Album | обязательное, `on_delete=CASCADE`, `related_name="album_songs"` |
| `song` | ForeignKey → Song | обязательное, `on_delete=CASCADE`, `related_name="album_songs"` |
| `track_number` | PositiveSmallIntegerField | обязательное, `>= 1` |

**Ограничение уникальности:** пара (`album`, `track_number`) уникальна — `unique_together`
(в Django ORM реализуется через `UniqueConstraint`).
Пара (`album`, `song`) также должна быть уникальной — одна и та же песня не может дважды
входить в один и тот же альбом.

### 2.5 ER-диаграмма (текстовое представление)

```
Artist (1) ──── (N) Album (1) ──── (N) AlbumSong (N) ──── (1) Song
                                        │
                                   track_number
```

## 3. Бизнес-правила

1. **Многократное использование песни.** Одна и та же запись `Song` может входить в разные
   `Album` через разные записи `AlbumSong`. Удаление песни из одного альбома не влияет на её
   присутствие в других альбомах.
2. **Уникальность номера трека в альбоме.** Порядковый номер (`track_number`) должен быть
   уникален в рамках одного альбома. Нельзя создать два трека с номером `3` в одном и том же
   альбоме. Уровень применения правила — база данных (constraint) + валидация на уровне DRF-сериализатора.
3. **Уникальность песни в альбоме.** Одна и та же песня не может быть добавлена в один и тот же
   альбом дважды (под разными или одинаковыми номерами).
4. **Целостность при удалении.**
   - Удаление `Artist` каскадно удаляет все его `Album` (и, соответственно, связанные `AlbumSong`).
   - Удаление `Album` каскадно удаляет все связанные `AlbumSong`, но не затрагивает сами записи `Song`.
   - Удаление `Song` каскадно удаляет все связанные `AlbumSong` (песня исчезает из всех треклистов),
     но не затрагивает альбомы и других исполнителей.
5. **Год выпуска.** `release_year` должен быть положительным целым числом в разумном диапазоне
   (не в будущем более чем на 1 год от текущей даты, не ранее ~1860 — условная дата начала звукозаписи).
6. **Нумерация треков не обязана быть непрерывной без пропусков** (допустимы 1, 2, 5 — заказчик не
   требует строгой последовательности), но `track_number` не может быть равен 0 или отрицательным.

## 4. Требования к UI (Vue 3 + Pinia + Vite)

### 4.1 Раздел «Исполнители» (Artists)

- Список всех исполнителей (с возможностью поиска/фильтрации по имени).
- Создание нового исполнителя (форма: имя).
- Редактирование имени существующего исполнителя.
- Удаление исполнителя (с предупреждением, что каскадно удалятся его альбомы).
- Переход со страницы исполнителя к списку его альбомов.

### 4.2 Раздел «Альбомы» (Albums)

- Список всех альбомов (с отображением исполнителя и года выпуска; фильтр по исполнителю).
- Создание альбома:
  - выбор/указание исполнителя (`artist`), названия (`title`), года выпуска (`release_year`);
  - формирование треклиста прямо в форме создания: добавление существующих песен из каталога
    ИЛИ создание новой песни «на лету», с указанием порядкового номера трека для каждой;
  - клиентская валидация уникальности номеров треков внутри формы до отправки на сервер.
- Редактирование альбома: изменение метаданных альбома, добавление/удаление треков,
  изменение порядковых номеров (drag-and-drop или числовые поля — на усмотрение реализации).
- Просмотр страницы альбома: метаданные + треклист, отсортированный по `track_number`.
- Удаление альбома (с предупреждением о каскадном удалении связей `AlbumSong`, песни при этом сохраняются).

### 4.3 Раздел «Песни» (Songs / Catalog)

- Каталог всех песен в системе (список, поиск по названию).
- Просмотр песни: карточка/страница песни показывает **все** альбомы, в которых песня встречается,
  с указанием номера трека в каждом из них (например: «Bohemian Rhapsody — A Night at the Opera, трек 11»,
  «Bohemian Rhapsody — Greatest Hits, трек 2»).
- Создание песни независимо от альбома (просто по названию) — опционально, для последующего
  добавления в альбомы из раздела «Альбомы».
- Редактирование названия / удаление песни (с предупреждением о том, что она исчезнет из всех треклистов).

### 4.4 Общие UI-требования

- SPA на Vue 3 (Composition API, `<script setup>`), маршрутизация (vue-router предполагается на шаге Plan).
- Состояние сущностей (artists/albums/songs) хранится и кэшируется в Pinia-сторах, с явными
  actions для CRUD-операций через DRF API.
- Отображение состояний загрузки и ошибок (в т.ч. ошибок валидации с backend, например конфликт
  `track_number`).
- Формы должны показывать понятные сообщения об ошибках, возвращаемых DRF (400 Bad Request с деталями).

## 5. Acceptance Criteria (Критерии приёмки)

### 5.1 Backend (Django + DRF)

- [ ] Модели `Artist`, `Album`, `Song`, `AlbumSong` реализованы согласно разделу 2, миграции применяются без ошибок.
- [ ] На уровне БД задан constraint уникальности пары (`album`, `track_number`) в `AlbumSong`.
- [ ] На уровне БД задан constraint уникальности пары (`album`, `song`) в `AlbumSong`.
- [ ] Попытка создать/обновить `AlbumSong` с дублирующимся `track_number` в рамках того же альбома
      возвращает `400 Bad Request` с понятным сообщением об ошибке (не `500`).
- [ ] Реализованы REST-эндпоинты (DRF ViewSets/Routers) как минимум для:
  - `GET/POST /api/artists/`, `GET/PUT/PATCH/DELETE /api/artists/{id}/`
  - `GET/POST /api/albums/`, `GET/PUT/PATCH/DELETE /api/albums/{id}/`
  - `GET/POST /api/songs/`, `GET/PUT/PATCH/DELETE /api/songs/{id}/`
  - Вложенное управление треклистом альбома (создание/удаление/переупорядочивание `AlbumSong`),
    например через nested-роут `/api/albums/{id}/tracks/` либо через вложенные сериализаторы —
    конкретная схема фиксируется на шаге Plan.
- [ ] `GET /api/songs/{id}/` возвращает (либо отдельный эндпоинт возвращает) список альбомов,
      в которых участвует песня, с номером трека в каждом.
- [ ] Удаление `Artist` каскадно удаляет его альбомы и связанные `AlbumSong` (проверяется тестом).
- [ ] Удаление `Song` удаляет связанные `AlbumSong`, но не затрагивает другие альбомы/песни (проверяется тестом).
- [ ] Удаление `Album` не удаляет связанные `Song` (проверяется тестом).
- [ ] Валидация `release_year` (диапазон) и `track_number` (>= 1) реализована на уровне сериализаторов.
- [ ] Набор автотестов (Django `TestCase`/DRF `APITestCase`) покрывает: создание сущностей, нарушение
      уникальности `track_number`, каскадное удаление, получение альбомов песни.
- [ ] API документировано (минимум — предсказуемые REST-контракты; схема/Swagger — опционально, решается на шаге Plan).

### 5.2 Frontend (Vue 3 + Pinia + Vite)

- [ ] Приложение собирается и запускается через Vite (`npm run dev`) без ошибок консоли.
- [ ] Реализован CRUD-интерфейс для исполнителей: список, создание, редактирование, удаление
      с подтверждением.
- [ ] Реализован CRUD-интерфейс для альбомов, включая привязку треков (существующих и новых песен)
      с указанием порядкового номера прямо в форме альбома.
- [ ] Форма альбома не позволяет отправить два трека с одинаковым номером (клиентская валидация)
      и корректно отображает серверную ошибку, если конфликт всё же произошёл (гонка/race condition).
- [ ] Реализован каталог песен со страницей песни, показывающей все альбомы и номера треков,
      в которых песня участвует.
- [ ] Все данные читаются/пишутся через Pinia-сторы, обращающиеся к DRF API (без прямых fetch-вызовов
      в компонентах, минуя стор).
- [ ] Обработаны и показаны пользователю состояния: загрузка, пустой список, ошибка сети/валидации.
- [ ] Удаление исполнителя/альбома/песни сопровождается предупреждением о каскадных последствиях
      (см. п. 3.4 бизнес-правил).
- [ ] Базовая адаптивность и отсутствие явных визуальных поломок на десктопном разрешении (мобильная
      адаптация — опционально, не входит в MVP, если не указано иное).

## 6. Вне рамок данной спецификации (Out of Scope)

Явно не входит в MVP (может быть добавлено на будущих итерациях, требует отдельной спецификации):

- Аутентификация/авторизация пользователей и разграничение прав доступа.
- Загрузка обложек альбомов и аудиофайлов.
- Полнотекстовый поиск/рекомендации/интеграция с внешними музыкальными базами (Spotify, MusicBrainz и т.п.).
- Многоязычность (i18n) интерфейса.
- Учёт продолжительности треков, жанров, лейблов и прочих метаданных — модель ограничена
  полями, перечисленными в разделе 2.
